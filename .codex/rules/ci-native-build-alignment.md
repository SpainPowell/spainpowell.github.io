## `react`/`react-native` Must Track Expo's Exact Tested Patch — CI and Dependabot Both Enforce This

**A patch-level Dependabot bump of `react-native` (0.83.6 → 0.83.10) and `react` (19.2.0 → 19.2.8) — well within
what the existing dependabot.yml ignore rule allowed ("block minor+major, allow patches") — silently broke the
iOS native build for every subsequent PR. Every cached simulator dev-client build then crashed on launch with
`RNGoogleMobileAdsModule could not be found`, and a fresh `pod install` failed outright.**

**Why:** `npx expo install --check` is the authoritative source for which exact versions Expo SDK 55 was tested
against — not "any 0.83.x"/"any 19.x". The drift to 0.83.10 tripped a codegen-parser incompatibility between
`react-native-screens`' spec file and RN 0.83.10's codegen (it errors on an Android-only spec even for an
iOS-only build target), which made `pod install` fail with exit code 1 for *any* fresh native build. Confirmed
during a Phase 3 UI-work session: three different-vintage cached `.app` builds (spanning ~2 weeks) all crashed
identically at JS-bundle-eval time, before any screen even rendered — and the actual native module registry
generated by codegen (`RCTModuleProviders.mm`'s `moduleMapping`) was a genuinely empty `@{ }`, for every module,
not just AdMob. That crash is a *symptom* of the broken codegen/pod-install step, not a standalone AdMod bug —
don't misdiagnose it as one.

**How this was fixed:** `npx expo install --check` also flagged `@react-native-async-storage/async-storage`
(3.1.1 vs expected 2.2.0), `react-native-view-shot` (5.1.1 vs expected 4.0.3), and `typescript` (6.0.3 vs expected
~5.9.2) as "outdated." **Do not blindly downgrade those to match** — verified via `tsc --noEmit` that doing so
breaks real app code: async-storage 2.2.0 lacks the `getMany`/`setMany`/`removeMany` batch API
`playersMapCache.ts`/`storage.ts` already depend on, and `react-native-view-shot` 4.0.3 doesn't export the
`ViewShotRef` named type ~10 files import. The app has already migrated to and verified against those newer
APIs — Expo's bundled compatibility table being conservative doesn't make the newer versions wrong. Only
`react`/`react-native` actually caused the native-build breakage; fix scope was narrowed to just those two
(`npx expo install react@19.2.0 react-native@0.83.6`), matching the precedent of the earlier, similarly-scoped
`react-native-screens`/`safe-area-context` hotfix (PR #222) — a targeted realignment, not a blanket
`expo install --fix` sweep.

**How to apply:**
- Before assuming a red-box crash on a fresh simulator build is an app/JS bug, run `npx expo install --check` in
  `mobile/` first. If `react` or `react-native` appear, that's very likely your actual cause — realign those two
  specifically, then re-verify with a **real** `pod install` (not just the standalone codegen script, which can
  succeed even when the full `pod install` invocation fails differently — confirm both).
- If `expo install --check` flags *other* packages too, don't reflexively fix all of them — run `tsc --noEmit`
  after test-installing Expo's suggested version for each. If it introduces new type errors, the app has already
  moved past that package's Expo-bundled version deliberately (or by accretion); leave it, and don't let a
  same-session urge to "fully align everything" turn a narrow native-build fix into an unplanned API migration.
- `.github/dependabot.yml` now blocks **every** update type (patch included) for `react` and `react-native` —
  they may only move together via `npx expo install`/`--fix` during a deliberate Expo SDK upgrade, never a lone
  Dependabot PR. If you need a newer RN for some other reason, that's an SDK upgrade decision, not a routine bump.
- `ci.yml`'s `test-mobile` job asserts the *installed* `react`/`react-native` versions equal the repo's verified
  pins (currently `19.2.0`/`0.83.6`, read via `node -p "require('react-native/package.json').version"`), rather
  than trusting `npx expo install --check`. That distinction matters: Expo SDK's *bundled* expected version can
  move ahead of what we can safely ship — Expo now expects react-native `0.83.10`, which re-breaks our native
  codegen, so we deliberately stay on `0.83.6`. The old approach (grepping `expo install --check` output for
  `react`/`react-native`) therefore started failing CI on our *correct* pinned versions the moment Expo's table
  advanced; asserting against explicit `EXPECTED_*` values in the step decouples us from that. When the verified
  pin legitimately changes (a real Expo SDK upgrade), bump the two `EXPECTED_*` values in that step. This still
  catches drift from *any* source, not just Dependabot (a manual `npm install`, a peer-dep resolution shift from
  an unrelated bump), and reading the resolved `package.json` version catches lockfile/transitive drift too. It is
  **not** a full native iOS build in CI (that's a bigger, separate cost/infra decision — CI still has no
  native-build step per `CLAUDE.md`) — it only catches this specific, previously-hard-to-detect failure mode
  cheaply, on the existing `ubuntu-latest` runner.
- When you actually need to rebuild a dev-client after this kind of fix, prefer `npx expo run:ios --device <UDID>`
  over a raw `xcodebuild -workspace ... build` invocation — the latter was observed to produce a **build that
  reports SUCCEEDED but generates a genuinely empty codegen module registry** (all native modules silently
  unregistered), because it skips environment setup (Node path resolution, `.xcode.env`-equivalent config) that
  Expo's own CLI wrapper provides to the codegen build-phase script. A green `xcodebuild` exit code is not
  sufficient evidence the build is actually functional — always launch and screenshot per
  `simulator-verification.md` before trusting it.
