## When Required PR Checks Won't Dispatch, Ask Copilot on the PR Before Spinning or Bypassing

**A required status check that is *absent* — GitHub never created a run for the head commit — is a different failure than one that is *red*. When the standard re-triggers don't produce a run and the merge is blocked, stop re-triggering: post a comment addressed to `@copilot` on the PR asking why the checks aren't dispatching, read its response, and act on it — before escalating to the user or reaching for an admin bypass.**

**Why:** During the UI-overhaul Phase 0 (PR #193), CI ran and passed on the first commit (`d9fe59f`), but GitHub Actions then **never dispatched a run for any later commit** — not on the `synchronize` push of a one-line `react-native-worklets` version pin, not after a close+reopen, not after a force-push to a fresh SHA (`573ce45`). A 15-minute watcher polled `gh run list --branch` and saw zero runs the whole time, while 8 other branches' CI runs dispatched and executed normally under heavy concurrent-agent load. `.github/workflows/ci.yml` had no `paths`/`concurrency`/`types` filters and Actions was enabled (`allowed: all`), so nothing in the repo config explained it — it was a GitHub-side dispatch problem. Branch protection required `test-mobile` + `test-backend`, so the PR was blocked on checks that simply would not start, and repeatedly re-triggering burned cycles for nothing.

**How to apply:**
- First confirm it is a *dispatch* problem, not a *failure*: `gh run list --branch <branch>` — is there any run for the head SHA at all? — and `gh pr view <n> --json statusCheckRollup,mergeStateStatus` (a head SHA with no run and `mergeStateStatus: UNKNOWN`/`BLOCKED` on required checks is dispatch, not red).
- Try the standard re-triggers **once each, not on a loop**: amend to a new SHA + `git push --force-with-lease` (cleanest, no noise commit), or an empty commit, or close+reopen the PR. Verify with `gh run list --branch` whether a run actually appeared.
- If a run still won't dispatch, **post a PR comment addressed to `@copilot`** that states: which checks are required, that no run exists for the head SHA, the exact re-triggers already tried, and the relevant `ci.yml` triggers — and ask why the workflow isn't dispatching and how to get the required checks to run. Then **read Copilot's reply and act on it** (`gh pr view <n> --comments` or poll `gh api repos/<o>/<r>/issues/<n>/comments`).
- Do **not** `gh pr merge --admin` or otherwise bypass required checks unilaterally to escape stuck CI — surface it to the user with the evidence and let them decide (re-run from the Actions UI, adjust branch protection, or authorize a bypass). A dep-only or docs-only commit cannot change lint/tsc/test outcomes, so the *code* may already be verified even when the *gate* is stuck: say so plainly, but still don't bypass without authorization.
- Don't stall the rest of the work on it. If later phases can proceed on a branch stacked on the blocked one, do that in parallel (see the worktree pattern) and let the stuck check resolve out of band.
